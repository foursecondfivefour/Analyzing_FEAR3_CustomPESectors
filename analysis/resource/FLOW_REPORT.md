# Продолжение: таблицы Resource, объекты и потоки вызовов

## Метод и границы

Это продолжение [`REPORT.md`](REPORT.md). Адреса ниже — **предпочитаемые VA** PE32/x86 с SHA-256 `caa1f80d49da5dbadee3b1a44c470a87ffcb6afa8c0ed24af01741a155c326c2`. `this` — обозначение для ECX на входе рассматриваемых методов, соответствующее наблюдаемому коду и соглашению MSVC x86; названия полей неизвестны. EXE не запускался.

В [`flow-snippets.txt`](flow-snippets.txt) — 32 воспроизводимых фрагмента инструкций с машинными байтами. Они начинаются в известных целях указателей таблицы либо в вручную проверенных границах; некоторые специально обрезаны и не являются целыми функциями. [`rename-stream-slots.csv`](rename-stream-slots.csv) содержит проверенные 11 слотов делегирования. Скрипт проверяет хеши входов, имена четырёх импортов, указатели выбранных слотов и шаблон всех 11 методов:

```sh
python tooling/resource_flow.py
```

Ниже разграничены наблюдаемые команды, вероятная интерпретация и неизвестное. Смещения вида `this+...` относятся к объектам **в памяти**, а `Resource+...` — к байтам исходной секции на диске.

## 1. `RenameStream`: устройство и делегирование

В секции на `Resource+0x7EC` находится RTTI с типом `.?AVRenameStream@Despair@@`; следующий указатель на `+0x7F0` начинает таблицу, адрес которой `0x19187F0`. На `0x8C6894` она реально записывается в `[esi]` создаваемого объекта. Поэтому связь данного кода с этой таблицей подтверждается не только похожим числом, но и самой инструкцией установки.

### Создание и освобождение

В отрывке `0x8C6870–0x8C68CA`:

1. `0x8C6873–0x8C6875`: в `0x868EC0` передаётся число `0x10`; результат проверяется на нуль. Это согласуется с выделением 16 байт, но назначение аллокатора без его разбора отдельно не утверждается.
2. При ненулевом результате вызывается `0x81E4E0`, затем в `[объект+0]` записывается адрес таблицы `0x19187F0`.
3. Значение из аргумента записывается в `[объект+8]`. Если оно ненулевое, вызывается `KERNEL32!InterlockedIncrement` с адресом `внутренний_объект+4`.
4. В `0x552F80` передаются адрес поля `объект+0xC` и другой аргумент. Эта функция сохраняет в поле указатель, полученный через `0x47EFB0`, и выполняет операции счётчика ссылок. Назначение и формат этого объекта ещё не установлены.
5. Результат записывается в выходной указатель; при ненулевом результате `InterlockedIncrement` вызывается также на `новый_объект+4`.

Первый слот таблицы (`Resource+0x7F0`) указывает на `0xA2E4A0`. Там при ненулевом `[this+0xC]` вызывается `0x8472A0`; если `[this+8]` ненулевой, вызывается `InterlockedDecrement` на адресе `внутренний+4`. Если результат не больше нуля, вызывается слот 0 внутреннего объекта с аргументом 1. Затем сбрасывается таблица, вызывается `0x8E1840` и, в зависимости от младшего бита входного аргумента, вызывается `0xBEB920` с адресом объекта. Это поведение **согласуется** с освобождением и управлением ссылками, но точные типы и семантика вызываемых функций требуют отдельной проверки.

### Все 13 наблюдаемых слотов таблицы

Индекс считается с адреса `Resource+0x7F0`.

| Индекс | Смещение в Resource | Цель | Доказанное по инструкциям |
|---:|---:|---:|---|
| 0 | `7F0` | `0xA2E4A0` | Описанный выше код освобождения/условного вызова. |
| 1 | `7F4` | `0x52D1A0` | Возвращает значение `[this+0xC] + 8`; не проверяет поле на нуль. |
| 2–12 | `7F8–820` | см. CSV | Берут внутренний объект из `[this+8]`, читают его таблицу и передают управление соответствующему слоту. |

Для 11 последних слотов соответствие точное: внешние индексы 2–12 пересылаются на смещения `0x08, 0x0C, …, 0x30` таблицы внутреннего объекта. Пример `Resource+0x7F8 → 0x56ED90`:

```asm
mov ecx, [ecx+8]   ; внутренний объект
mov eax, [ecx]     ; его таблица
mov edx, [eax+8]   ; слот внутренней таблицы
jmp edx
```

Другие десять используют ту же схему; у некоторых для цели используется EAX, а не EDX. Перед косвенным переходом проверка `[this+8]` на нуль в этих обёртках отсутствует. Названия операций чтения, позиционирования и т. п. из одного этого шаблона **не установлены**. Доказано делегирование без изменения аргументов на стеке в самом показанном коде (ECX заменяется внутренним объектом), а не предназначение каждого слота.

## 2. `ResourceMgr2`: vptr и поля состояния

RTTI на `Resource+0x57C` и `+0x588` указывает на `ResourceMgr2`, с `offset` подобъекта соответственно 4 и 0. В процедуре, начинающейся на `0xAFF210`, после копирования ECX в ESI наблюдается:

```asm
mov dword ptr [esi],   0x191858c ; Resource+58C
mov dword ptr [esi+4], 0x1918580 ; Resource+580
...
mov dword ptr [esi+0x2c], 0
mov dword ptr [esi+0x30], 0
mov dword ptr [esi+0x34], 0
mov dword ptr [esi+0x38], 0
mov dword ptr [esi+0x3c], 0
mov dword ptr [esi+0x40], 0
mov byte ptr  [esi+0x44], 1
```

Это подтверждает установку двух соответствующих таблиц и начальное состояние указанных полей **в этой процедуре**; значения позднее могут измениться. В той же процедуре ненулевые входные ссылки увеличиваются через `InterlockedIncrement`. Не следует приписывать всем полям имена по одному начальному значению.

Отдельные цели таблицы позволяют точно восстановить следующие операции:

| Смещение слота | Цель | Операция |
|---:|---:|---|
| `+5CC` | `0x6AA760` | Копирует младший байт аргумента в `[this+0x44]`, `ret 4`. |
| `+5D0` | `0x69E000` | Возвращает байт `[this+0x44]` в AL. |
| `+5D4` | `0x6CEDB0` | Читает `p=[this+0x40]`, затем `q=[p+0x34]`; пишет аргумент в байт `[q+0x1D]`. |
| `+5D8` | `0x9F80E0` | По тем же двум указателям возвращает `[q+0x1D]`. |
| `+5DC` | `0xCFC250` | По тем же двум указателям записывает байт `[q+0x1E]`. |
| `+5E0` | `0x67B130` | По тем же двум указателям читает байт `[q+0x1E]`. |
| `+5F4` | `0xC2D6F0` | Возвращает адрес поля `this+0x28`. |

Проверок указателей `p` и `q` на нуль в самих приведённых методах нет. Пока не доказано, какой именно настройке соответствуют поля `+1D` и `+1E`, и нельзя без дополнительного анализа напрямую приравнять одно из них к строке `dvdEmulationEnabled`.

## 3. Путь от job-wrapper к диагностике

`Resource+0x624` содержит RTTI `ResourceJobWrapper`; один из следующих слотов, `+0x62C`, указывает на `0x6EFE90`:

```asm
mov ecx, [ecx+8]
jmp 0xE3D9F0
```

Таким образом при вызове этого слота управление передаётся объекту из поля `+8`. Цель `0xE3D9F0` содержит цикл и вызовы других функций. На `0xE3DA61` код читает указатель из `[esi+0x18]`; если байт объекта по `+0x1E` равен нулю, показанная диагностическая ветка обходится. Внутри ветки выполняются вычисления с числами x87, а на `0xE3DA86` функции `0x7BF7D0` передаётся `0x19186F4` — адрес строки `\nResourceJob::Execute()` в Resource. Ещё одно такое обращение находится на `0xE3DB38`.

Это подтверждает связь таблицы wrapper → функция `0xE3D9F0` → строка диагностики. Само имя строки не доказывает формальную сигнатуру функции, смысл x87-сравнения или то, что адрес `[esi+0x18]` совпадает с объектом `q` из предыдущего раздела.

## 4. Генерация FlexML-пути и форматирование

В отрывке `0x8DD489–0x8DD4D4`, выполняемом при определённом условии в окружающей функции:

1. Из `[ebp+0x1C]` извлекается поле `+0x1C`; при нулевом значении вместо него используется адрес пустой строки `Resource+0x116`.
2. Из `Resource+0x6B8` читается 32-битное значение, начальные байты которого в PE равны нулю.
3. Значение и строка передаются вместе с форматом `/flexml/by/stream/%i.%s` (`Resource+0x6DC`) и адресом буфера в функцию `0x942E50`.
4. Эта функция передаёт аргументы `MSVCR90.dll!_vsnprintf` (IAT `0x13F066C`), в том числе длину `0x1FF`; результат записывает в начало структуры. Затем она явно записывает NUL по `структура+0x203`. Указанный буфер начинается с `структура+4`; установленный NUL расположен на индексе `0x1FF` этого буфера.
5. Возвращённый адрес смещается на 4, длина строки вычисляется через импорт `std::char_traits<char>::length`, и вызывается `0xC795D0`. После этого `inc dword ptr [0x19186B8]` увеличивает глобальное значение.

Следовательно, здесь действительно вызывается форматирование строки с целым значением и суффиксом; это сильнее прежней гипотезы, основанной только на форматной строке. В показанной инструкции `inc` нет префикса `lock`; из этого **нельзя** само по себе заключить, что возможна гонка в реальном исполнении: неизвестно, какие внешние блокировки и потоки защищают этот участок. Не установлено, является ли путь файловой системой, внутренним идентификатором или обеими вещами.

## 5. `FlexMLWrapperLoadResource`: минимальная семантика

RTTI на `Resource+0x714` называет `FlexMLWrapperLoadResource`, а таблица далее содержит:

- `Resource+0x71C → 0x861060`: записывает адрес `0x1918750` в указатель, переданный аргументом; этот адрес — `Resource+0x750`.
- `Resource+0x720 → 0xBEEDC0`: записывает аргумент в `[this+8]`.
- `Resource+0x724 → 0xB530C0`: возвращает `[this+8]`.
- `Resource+0x72C → 0xA71E30`: возвращает 0 в EAX.

Эти результаты — точные операции на инструкциях. Тип поля и смысл возвращаемого нуля пока не определены. На уровне статического содержимого `Resource+0x750` состоит из нулей, но эта область используется как адрес данных и может изменяться во время работы.

## 6. Что остаётся невыясненным

Полные тела сложных методов, имена интерфейсных слотов, жизненный цикл очередей, условия блокировки, формат загружаемых ресурсов и фактические действия внешних библиотек здесь не восстановлены. Образец сам по себе не содержит PDB или базы IDA; возможны косвенные вызовы и дополнительные ссылки, невидимые по поиску абсолютных адресов. Для ответа о runtime-состоянии нужны отдельная безопасная Windows-среда, зависимости и трассировка; ни запуск, ни такая трассировка не выполнялись.
