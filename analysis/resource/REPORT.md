# Статический разбор `15_Resource.bin`

## 1. Границы, идентичность и способ чтения

Образец не запускался. Его SHA-256: `6e4679833292366db29855d40f4f32734028740291142b9d1ffc2e62cb7e9ec6`. Использованный EXE: `caa1f80d49da5dbadee3b1a44c470a87ffcb6afa8c0ed24af01741a155c326c2`. Секция совпадает с диапазоном EXE побайтно. Исходный PE — x86/PE32, предпочитаемая база `0x400000`.

| Параметр | Значение |
|---|---:|
| 8 байтов имени секции | `52 65 73 6F 75 72 63 65` (`Resource`) |
| Индекс в таблице секций | 15, начиная с 0 |
| Размер в файле | `0xA00` = 2560 байт |
| VirtualSize | `0x824` = 2084 байта |
| RVA начала | `0x1518000` |
| Предпочитаемый VA начала | `0x1918000` |
| Смещение начала в EXE | `0x149EC00` |
| Последний байт в файле секции | `0x9FF` = `00`; в EXE `0x149F5FF` |
| Последний ненулевой байт | `0x822` = `6A` |
| Характеристики | `0xC0000040`: initialized data, read, write; бит execute не установлен |

Для смещения `o` внутри секции: смещение EXE = `0x149EC00 + o`; RVA = `0x1518000 + o`; предпочитаемый VA = `0x1918000 + o`. В `bytes.csv` VA для байтов вне VirtualSize — только арифметический результат, **не утверждение о доступности в памяти процесса**. Адреса — не адреса исполняемого файла на диске и не гарантированные адреса конкретного запущенного процесса.

Нулевых байтов 1704, ненулевых 856; энтропия всех 2560 байтов 3.035105 бит/байт. Последовательность от `0x823` по `0x9FF` включительно содержит 477 нулей: первый (`0x823`) ещё в пределах VirtualSize; остальные 476 байтов (`0x824–0x9FF`) лежат за его пределом и являются сырым хвостом секции. Нули **внутри** VirtualSize нельзя все объявить выравниванием: некоторые из них — начальные значения используемых кодом глобальных объектов или указателей.

## 2. Покрытие каждого байта и файлы результата

- `bytes.csv`: ровно **2560 строк данных**, по одной на каждый байт `0x000–0x9FF`, включая значение, обе системы адресов и предварительную категорию. Строки и указатели размечены для навигации, а не как абсолютное доказательство типа.
- `words.csv`: все **640** выровненных 32-битных слов в little-endian; численное попадание в секцию образа само по себе не доказывает, что слово — указатель. Поэтому значения, перекрывающие строки, отмечены отдельно.
- `hexdump.txt`: полный последовательный дамп, без пропусков.
- `inventory.json`: все 256 частот байтов, строки, кандидаты указателей, разобранные RTTI и иерархии.
- `address_matches.csv`: все **377** совпадений четырёх байтов с диапазоном предпочитаемых адресов секции в EXE на любом байтовом выравнивании. Это поиск паттерна, не список доказанных ссылок. Столбец инструкций показывает возможные декодирования вокруг совпадения; границы x86-инструкций не подтверждены только этим сканированием.
- `text_target_previews.txt`: короткие дизассемблированные начала у 92 различных предполагаемых адресатов в `.text`, не полные функции.

Реестр разбивает байты на 424 байта наблюдаемых строк, 34 их NUL-терминатора, 540 байтов слов-кандидатов указателей, один прочий ненулевой байт и 1561 прочий нулевой байт. Это техническая разметка покрытия, а не утверждение, что остальные нули не используются. Единственный прочий ненулевой байт — `0x0A` на `0x678`, в слове `0A 00 00 00` (= 10); его назначение не установлено.

Повторить:

```sh
python tooling/verify.py --exe 'evidence/source-exe/F.E.A.R. 3.exe'
python tooling/analyze_resource.py
```

Скрипт требует зафиксированные SHA-256 обоих входов, проверяет срез EXE и отказывается продолжать при несовпадении. PE и инструкции разбираются `pefile` и Capstone из `tooling/python`. Это статическое чтение, не выполнение EXE.

## 4. Указатели, RTTI и классы

Среди выровненных слов, не перекрывающих отмеченные строки, 135 значений попадают в адресные диапазоны PE: 108 — в `.text`, 26 — в `.rdata`, одно — в саму `Resource`. Это **кандидаты**, а не гарантия типа каждого слова. Пояснение: несколько ASCII-слов тоже численно попадают в диапазон `.text`, поэтому просто считать все попавшие числа указателями неверно; строки отфильтрованы.

Все 26 указателей в `.rdata` имеют согласующуюся с 32-битным MSVC форму RTTI Complete Object Locator: нулевая сигнатура, смещение подобъекта, указатель TypeDescriptor с декорированным именем и указатель Class Hierarchy Descriptor. Детальные данные и поля всех дескрипторов — в `inventory.json`. Форма и расположение соответствуют таблицам виртуальных функций, хотя точные границы каждого метода без более глубокого управления потоком не доказаны.

| Смещение поля с RTTI | Декорированный тип (пространство `Despair`, если не указано иное) | Смещение подобъекта |
|---|---|---:|
| `12C`, `134` | `IResource` | 4, 0 |
| `1D4`, `1E0` | `WorkspaceItem`, `Workspace` | 0, 0 |
| `350`, `364`, `36C` | `UniqueResource` | 12, 4, 0 |
| `510` | `IResourceCreator` | 0 |
| `57C`, `588` | `ResourceMgr2` | 4, 0 |
| `624` | `ResourceJobWrapper` | 0 |
| `64C` | `IResourceLibrary` | 0 |
| `664`, `66C` | `ManagedResourceLibrary` | 4, 0 |
| `67C`, `684` | `MakerRegistry2::FlexMLMakerExtensionReceipt`, `MakerRegistry2` | 0, 0 |
| `68C`, `694` | `MakerRegistry2::FileMakerReceipt`, `MakerRegistry2::FlexMLMakerReceipt` | 0, 0 |
| `69C` | `InstanceFactory` | 0 |
| `6A4`, `6AC` | `UnmanagedResourceLibrary` | 4, 0 |
| `6BC` | `RequestCaptor2` | 0 |
| `70C`, `714` | `FlexMLWrapperLoadResource` | 4, 0 |
| `7E4`, `7EC` | `LoadRequest`, `RenameStream` | 0, 0 |

RTTI для `ResourceMgr2` перечисляет также `IResourceMgr`, `IResourceCreator`, `Reflection::Object` и `boost::noncopyable_::noncopyable`. RTTI для managed и unmanaged library перечисляет `IResourceLibrary`, `AtomicRefCounted`, `boost::noncopyable`; это сведения таблиц RTTI об иерархии, а не расшифровка реализации. У `FlexMLWrapperLoadResource` в иерархии указаны `ResourceBase`, `IResource`, `Reflection::QueryObject`, `Reflection::Object`, `Reflection::IQueryObject`. Подробности со смещениями — в машинном отчёте.

13 слов (`+140–14C`, `+514–52C`, `+650–654`) содержат один адрес `0xF3B326`. По этому VA находится инструкция `jmp dword ptr [0x13F06A4]`; IAT `0x13F06A4` разрешается в импорт `MSVCR90.dll!_purecall`. При этом `0x9F9B12: mov dword ptr [esi], 0x1918514` записывает адрес первого такого слота после RTTI `IResourceCreator` в объект — дополнительное свидетельство виртуальной таблицы. Отдельно `+310` хранит адрес `0x1918330`, соответствующий строке `ResourceHandle Uninitialized` в самой секции.

Адреса `0x1216F60`, `0x1216F70`, `0x1216F80` выглядят как adjustment thunks: первые инструкции `sub ecx, 4` и переход соответственно на `0x874340`, `0xADD620`, `0x62F420`. Это согласуется с RTTI со смещением подобъекта 4, но не определяет назначение методов.

## 5. Подтверждённые примеры использования и осторожные выводы

Ниже адреса инструкций — предпочитаемые VA; конкретные инструкции декодированы с проверенных границ, в отличие от сырых поисковых совпадений.

1. В `0x13016E0–0x1301700` код читает значение из `0x1918058` (секция `+058`), если оно равно нулю, передаёт строку `Resource\RequestHandle` (`+060`) функции `0x879F40`, сохраняет результат в `+058` и `+05C`. Это наблюдаемая ленивая инициализация/кэширование; семантика вызываемой функции без дальнейшего анализа не установлена.
2. В `0x1301710` код передаёт строку `ResourceBase` (`+078`) и адрес объекта `+088` функции `0xE6A0A0`. Аналогичный шаблон на `0x13017D0` связывает `WorkspaceItem` (`+200`) и адрес `+240`. Это подтверждает использование нулевых областей как данных для инициализации, но точная схема регистрации не доказана одним фрагментом.
3. Инструкции `0x51DEDF` и `0x51DF2F` передают строки `file` и `name` соответственно. Они показывают реальное использование строк, но не определяют самостоятельно формат файла.
4. На `0x8DD493–0x8DD4CE` код выбирает указатель на пустую строку при нулевом значении, читает 32-битное значение по `+6B8`, передаёт формат `/flexml/by/stream/%i.%s` по `+6DC` функции `0x942E50` и увеличивает значение по `+6B8`. По этому фрагменту можно предположить построение имени с номером и суффиксом; точные типы аргументов и многопоточная безопасность не установлены.
5. На `0xE3DA86` и `0xE3DB38` код передаёт адрес `+6F4` (LF плюс `ResourceJob::Execute()`) функции `0x7BF7D0`. Содержание указывает на диагностику, но природа вызова не доказана без разбора `0x7BF7D0`.
6. На `0xAFF440` код передаёт `Resource Loader Thread` (`+558`) через виртуальный вызов. Сама строка и её передача не доказывают отдельно жизненный цикл или настройки потока.
7. На `0x13C0516` код передаёт `dvdEmulationEnabled` (`+610`) функции `0xEE8B20` вместе с адресом `+4A8` и другими аргументами. Название указывает на возможную опцию; её значение по умолчанию и последствия не установлены.

## 6. Ограничения

Продолжение с проверкой реализаций методов и форматирования: [`FLOW_REPORT.md`](FLOW_REPORT.md).

Это полный **учёт байтов** и разбор доказуемых структур, а не полное восстановление исходного кода. Статический снимок не показывает значения после инициализации, косвенные ссылки, все потоки исполнения, назначение каждого поля или подлинность EXE. Часть совпадений адресов может быть случайной; немедленное число может совпасть с адресом. Нужны анализ потока управления и косвенных вызовов, проверка структуры объектов, а для runtime-утверждений — отдельная изолированная среда и трассировка. Отсутствие находки при поиске абсолютного VA не означает отсутствия обращения через регистр или вычисленный адрес. `Resource` — пользовательская секция, не стандартная секция Windows `.rsrc`; по приведённым данным нельзя объявлять её отдельным архивом, DLL, шифром или всем ресурсным менеджером игры.
