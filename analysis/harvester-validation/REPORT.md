# Проверка комбайна и оставшихся RTTI-кандидатов

## Объект и метод

Анализировался **локальный, не запускавшийся** PE32 x86 размером 22 411 776 байт, SHA-256 `caa1f80d49da5dbadee3b1a44c470a87ffcb6afa8c0ed24af01741a155c326c2`. Хеш идентифицирует исследованный файл, но не доказывает подлинность или совместимость с другими сборками. Все адреса — preferred VA для image base `0x400000`, не адреса процесса после ASLR.

`tooling/validate_rtti_candidates.py` использует отдельный `pefile`-парсер и непосредственно проверяет байты секций, адреса, структуры и связи индексных CSV. Он **не** вызывает функции комбайна для проверки этих структур. `tooling/verify_cpp_classes.py` дополнительно независимо проверяет полноту найденных в сырых секциях `.?A` и кандидатов COL/vtable по своим опубликованным правилам. Скрипт записывает сводку и файл с индивидуальными свидетельствами; генераторы исходных CSV и оба проверяющих скрипта имеют общие предположения о формате RTTI MSVC x86, поэтому не являются полностью независимыми интерпретациями ABI.

Проверены SHA и метаданные **всех 35 raw-секций**; 31 предоставленная отдельным файлом секция побайтно совпадает с EXE. `section-validation.csv` содержит хеш и количество проверенных RTTI-дескрипторов и vtable-кандидатов по каждой секции. При отсутствии полного EXE режим `--extracted` покрывает лишь эти 31 секцию и не может подтвердить остальные четыре.

## Проверка 50 команд

`tooling/validate_harvester_commands.py` провёл по одному интеграционному примеру для **каждой из 50 команд**, проверяя не только успешный код возврата, но и конкретные значения. Сведения о каждой команде и параметрах — в `command-validation.json`. На реальных байтах PE сверены чтение и поиск, VA/смещение через `pefile`, хеши через `hashlib`, числа через `struct`, первые инструкции через Capstone, частоты, преобразование XOR, метаданные/экспорты, указатели и проверки класса. Отдельный поиск 12 первых байт каждой секции, включая перекрывающиеся совпадения, сравнен с независимым Python `bytes.find` по всем 35 секциям; всего шесть негативных сценариев завершились ожидаемой ошибкой. При большом числе совпадений в сравнении адресов проверяется максимум первых 1 000, но общее число сравнивается полностью.

Это **не исчерпывающее доказательство корректности всех входов** 50 команд и не утверждение, что каждая из них прочитала все секции. `pack`, `int-info`, `float-info`, операции с таблицами и часть индексных команд по назначению не читают PE; для некоторых из них использованы значения, извлечённые из PE, а для остальных — сохранённые индексы. У них есть также синтетические тесты в `tooling/test_*.py`. Выводы статические; `disasm` линейно декодирует выбранные пользователем байты, не строит гарантированный CFG.

## RTTI, COL, базовые типы и vtable

Повторно проверены каждое из **11 951** имён и заголовков TypeDescriptor, все **15 473** записи COL и их связи с иерархиями, все **9 656** иерархий и **38 310** строк base descriptor. Для каждого из **15 474** сохранённых vtable hits сверены предыдущий COL, TypeDescriptor, первый слот и его raw-backed executable-адрес. Из них 15 473 удовлетворяют правилам кандидата, один (`0x7C8D99` в `.text`) правильно отклонён как невыровненный hit в исполняемой секции. Первые инструкции декодируются для всех 15 473 принятых таблиц (8 078 уникальных адресов); это **не** подтверждает начало функции, длину таблицы или выполнение.

Точный список проверенных записей находится в `analysis/cpp-classes/classes.csv`, `complete-object-locators.csv`, `base-descriptors.csv`, `vtable-candidates.csv`; они являются входом проверяющих программ. Байтовое совпадение структур подтверждает **согласованность с форматом и связями**, а не гарантирует, что каждый кандидат является действительным объектом во время работы.

## 2 295 дескрипторов без найденного COL

В `no-col-evidence.csv` есть отдельная строка для каждого из 2 295 дескрипторов: адрес, имя, число вхождений в base descriptors, raw-ссылки, адреса найденных шаблонов, эвристические точки входа и уровень статического свидетельства. Группы ниже взаимно исключают друг друга и суммируются в 2 295:

| Наилучшее наблюдаемое свидетельство | Дескрипторов | Что именно подтверждено |
|---|---:|---|
| Base descriptor в проверенной COL-иерархии | 1 540 | Прямые сырые указатели и согласованные структуры RTTI, а не обязательно непосредственная базовость: база может быть транзитивной. |
| `type_info::operator==`, достигнутый по ограниченному CFG от эвристического входа | 511 | Декодируемая последовательность `push TD; call [IAT]`, вызов IAT MSVCR90 `??8type_info@@QBE_NABV0@@Z`. |
| Запись TD, достигнутая по ограниченному CFG | 175 | Последовательность с записью TD по адресу, взятому из аргумента; в этой категории comparison-шаблон не был достигнут согласно выбранной эвристике. |
| Только подходящие байтовые шаблоны кода | 68 | Байты присутствуют в executable-секции, но найденные CFG-начала не подтвердили границы последовательности. Остаются **неподтверждёнными как инструкции**. |
| Метаданные исключения и кандидатная цепочка вызова | 1 | `std::bad_cast`; см. ниже. |

Все 2 295 имеют хотя бы одно сырое 32-битное совпадение с адресом TD в 35 секциях; само по себе оно может быть случайным и не является семантической ссылкой. Из 755 без COL и без base descriptor **754** имеют шаблон сравнения, **753** — шаблон записи; эти числа перекрываются. Для 511 и 543 соответственно последовательность достижима при анализе от ближайшего предполагаемого входа после INT3-padding в ограниченном окне. Объединение двух CFG-категорий — 686, а не их сумма. Эвристика может промахиваться: косвенные переходы, вызовы и внешние входы не исследуются, якорь не доказывает начало функции, анализ не демонстрирует runtime-выполнение.

### Ручные контрольные точки

* `boost::io::basic_oaltstringstream<...>::No_Op`, TD `0x16E12E8`: в `.text` от кандидата входа `0xE02D40` последовательно декодируются `push 0x16E12E8` по `0xE02D47` и `call dword ptr [0x13F0680]` по `0xE02D4C`. Импорт по этому IAT — `MSVCR90.dll!??8type_info@@QBE_NABV0@@Z`. Это сильное статическое свидетельство соответствующей операции с type_info, но не факт её выполнения.
* `std::bad_cast`, TD `0x164167C`: CatchableType-подобная структура `0x16103E0` содержит этот TD и `(mdisp=0,pdisp=-1,vdisp=0,size=12,copy=0xF3B754)`; на неё указывает массив `0x16103D4`, на который указывает ThrowInfo `0x16103C4`. От эвристического начала `0x8871B0` ограниченный CFG достигает `push 0x16103C4` (`0x887214`), передачи адреса объекта и `call 0xF3B346` (`0x88721E`); там `jmp [0x13F0688]`, IAT `_CxxThrowException`. Статическая цепь хорошо согласуется с throw metadata, но факт выполнения и реальная динамическая типизация объекта не доказаны.
* Пример оставшихся сырых, не CFG-подтверждённых: TD `0x1624378` имеет подходящие byte patterns по `0x5277C0` и `0x6E64F2`. Не следует описывать их как доказанные вызов и запись только из-за совпадения байтов.

Таким образом, для всех 2 295 получены дополнительные индивидуальные статические свидетельства, но **68 кодовых паттернов не удалось поднять выше сырого совпадения**, а ни для одного класса не доказаны runtime-инстанцирование или полная реализация. Отсутствие обнаруженного COL не доказывает отсутствие vtable.

## Воспроизведение

Требуется локальная копия проверенного EXE в `evidence/source-exe/F.E.A.R. 3.exe` и опциональные пакеты, устанавливаемые через Python:

```sh
python -m pip install --target tooling/python pefile==2024.8.26 capstone==5.0.9
python tooling/verify.py --exe 'evidence/source-exe/F.E.A.R. 3.exe'
python tooling/verify_cpp_classes.py
python tooling/validate_rtti_candidates.py
python tooling/validate_harvester_commands.py
python -m unittest discover -s tooling -p 'test_*.py' -v
```

Оба новых валидатора требуют совпадения SHA-256 EXE. Первый поддерживает `--exe` и `--out`, при невалидном EXE отказывает до записи результатов. `validate_harvester_commands.py` записывает только свой JSON-отчёт. Никакие команды не запускают исследуемый EXE.
