# MiniPack, ZLib, LSD и LZD: статическая трассировка

## Главный результат

В исследованном EXE подтверждены **MiniPack**, **ZLib**, **LZD**, а также **LZX**. Строка `LSD` не найдена в EXE, извлечённых секциях и доступном снимке Lua/API в ASCII, UTF-16LE или UTF-16BE. Наиболее близкая реально подписанная тройка в EXE — **ZLib / LZX / LZD**; называть LZD «LSD» нельзя. Отсутствие буквальной строки не доказывает отсутствия алгоритма, закодированной строки или реализации под другим названием.

Важная граница: `MiniPackFileSystem`, `PackFileSystem` и `StreamCompression` — разные подтверждённые RTTI-типы. Путь `PackFileSystem → имена кодеков` и путь обработки блоков `StreamCompression → соответствующие ID` установлены статически; **прямое соединение именно MiniPack с этими потоками или утверждение, что каждый MiniPack использует ZLib/LZD, в этом анализе не доказано**. Общие числовые ID и соседство данных сами по себе не доказывают передачу объекта между этими классами.

## Объём и воспроизводимость

* EXE: 22 411 776 байт, SHA-256 `caa1f80d49da5dbadee3b1a44c470a87ffcb6afa8c0ed24af01741a155c326c2`; PE32 x86, preferred image base `0x400000`. Все адреса кода ниже — preferred VA, не file offsets и не runtime VA после ASLR.
* Сопоставление: 31 извлечённая секция проверена с EXE; `verify.py` подтвердил 35 хешей и побайтовое соответствие секций. Это подтверждает согласованность свидетельств, но не происхождение или подлинность EXE.
* Внешний Lua/API: закреплённый снимок commit `4a7a7cf3d48f09dca446441d8af427f30556280d`, ZIP SHA-256 `1f3aa0fb555a8e2bbb05b04b6464aa49951416baaed568e5963440b6ea2b80e6`. Проверены состав и SHA-256 всех 622 файлов относительно ZIP. Связь снимка с конкретно этим EXE не подтверждена. Оригинальные игровые архивы и бинарный luasense отсутствуют.
* Автоматический поиск: весь EXE + 31 секционный `.bin` + все 622 файла снимка, включая бинарные файлы. Искомые последовательности `minipack`, `zlib`, `lsd`, `lzd`, `lzx`, без учёта регистра ASCII, в ASCII, UTF-16LE и UTF-16BE. Файлы секций дублируют байты EXE: их совпадения **нельзя складывать** как независимые свидетельства. Иные кодировки, сжатые или генерируемые строки этим поиском не покрыты.
* EXE и upstream-код не запускались; ниже — статический анализ. Доказательство адресов не является доказательством достижимости конкретной ветви в игре.

Результаты: [`literal-hits.csv`](literal-hits.csv) — полный список найденных буквальных вхождений с путями и смещениями; [`codec-id-byte-hits.csv`](codec-id-byte-hits.csv) — все сырые вхождения трёх little-endian ID в EXE; [`rtti-vtables.csv`](rtti-vtables.csv) — проверенные RTTI и слоты; [`code-excerpts.txt`](code-excerpts.txt) — дизассемблирование; [`xref-candidates.csv`](xref-candidates.csv) — ограниченный поиск raw `push imm32` на выбранные строки и `call rel32` на выбранные функции. У последнего файла результаты **кандидаты**, пока граница инструкции не подтверждена; косвенные вызовы, другие формы ссылок и любые иные цели он не перечисляет.

## 1. Создание и методы MiniPack

1. `0x947780` проверяет вход через `0x512AC0`. При положительном результате получает/инициализирует ресурс с меткой `IO\\MiniPack`, выделяет `0x6C` байт и по `0x9477D6` вызывает конструктор `0x8E6710`. Затем `0x9477EE` вызывает `0xCED7B0`; при ошибке по результату виден путь очистки объекта. Точное назначение всех аргументов и семантика проверки не восстановлены.
2. `0x8E671E` записывает vptr `0x17EDBEC`. Его расположенный непосредственно перед таблицей MSVC complete-object locator `0x150CFD8` указывает на type descriptor `0x16AD238` с именем `.?AVMiniPackFileSystem@Despair@@`. Это проверяемая связь типа и таблицы, а не только соседство строк.
3. Слот таблицы `+0x04 → 0x969750` форматирует сообщение об добавлении MiniPack; `+0x68 → 0x4C31B0` форматирует отображение MiniPack к корню `/`. Приведённые имена из сообщений не гарантируют, что все эффекты методов известны.
4. `0xCED7B0` условно выводит строку об инициализации, затем продолжает обработку входов. Извлечён и RTTI `MiniPackFileDir`: type descriptor `0x16C91E0`, COL `0x150D304`, vtable `0x17EE594`. Также существуют RTTI `IMiniPackFileSystem`, `IMinipackResourceComponent`, `MiniPackModelComponent` и шаблон `GameMaker<MiniPackModelComponent>`; наличие имени типа не доказывает используемый runtime-экземпляр. Строки `IMinipackResourceComponent` и `MiniPackModelComponent` в `Game_dat` имеют raw `push`-кандидаты `0x1228370` и `0x1335160` соответственно; назначение этих вызовов здесь не реконструировано.

## 2. PackFileSystem: хранение ID и диагностическое имя

Конструктор `0x8D1F40` устанавливает vptr `0x17EE254`; COL `0x150D0B8` указывает на RTTI `.?AVPackFileSystem@Despair@@`. При `0x8D203A` он записывает ID `0xC5735A0F` в поле объекта `+0x114`: это **начальное значение**, а не доказательство выбранного формата каждого файла.

Функция `0xAA9AC0`, вызываемая из `0x9505F3`, читает данные через виртуальный интерфейс и при прохождении проверок использует флаги поля `+0x148`. Код `0xAA9CB1–0xAA9CE5` устанавливает поле `+0x114` по приоритету:

| Проверяемая маска | Значение поля `+0x114` | Имя из независимой диагностической ветви |
|---:|---:|---|
| `0x08` | `0xC5735A0F` | ZLib |
| `0x10`, если `0x08` не установлена | `0xC5735A10` | LZX |
| `0x20`, если первые две не установлены | `0xC5735A11` | LZD |
| ни один бит | запись в показанной ветви отсутствует | предыдущее значение; не обязательно UNKNOWN |

Порядок важен: при нескольких установленных битах побеждает первая проверка. Названия и значение `UNKNOWN` доказываются таблицей команд диагностического метода `0xA767C0`, присутствующего в vtable PackFileSystem по слоту `+0x68`. После виртуального вызова `[vtable+0x70]` он формирует текст `AllowDuplicates` при бите 1, `InternalCompression` при бите 2 и `MiniPack` при знаковом бите возвращённого значения. Для вывода `Compression:` он при установленном бите 2 сравнивает поле `+0x114` с тремя ID (`0xA76CCA–0xA76CD8`) и выбирает соответствующую строку или `UNKNOWN`. Следовательно, эта ветвь доказывает **соответствие ID и диагностических имён**, а не сама по себе компрессию или декомпрессию.

## 3. StreamCompression: чтение блока и ветвление по ID

Конструктор `0xA47730` устанавливает vptr `0x17EE3B8`; COL `0x150D124` связывает таблицу с `.?AVStreamCompression@Despair@@`. Слот `+0x18 → 0xC19890` вызывает обработчик блока `0xA50420` на `0xC198DC` при необходимости пополнить данные. Непосредственный вызов также есть на `0x52E1D2`.

* `0x552230 → 0xA47730 → 0x839990`: после выделения и конструирования `0x839990` считывает 32 байта через виртуальный метод источника, затем сравнивает ID в `+0x10` с тремя значениями. `0xDE20F0 → 0xA47730 → 0x52E0D0` использует другой путь, копирующий 32 байта из предоставленного буфера, и проводит аналогичные проверки. Оба пути устанавливают `+0x4D = 1` для ZLib-ID, `0` для LZX/LZD; LZX дополнительно вызывает `0x6BE3A0` и `0x7BAA80`. Неподдержанный ID отправляется в отдельную ветвь отказа. Нельзя считать этот 32-байтный фрагмент полным описанием формата.
* `0xA50420` вычисляет индекс блока, проверяет границы, вызывает виртуальные операции источника, читает данные и выбирает ветвь. При `+0x4D != 0` применяется виртуальный обработчик `+0x50` при определённых условиях, иначе вызов `0xE5A3A0` на `0xA5055F`; метка ZLib вытекает из приведённой выше инициализации и сопоставления ID, а не из имени функции.
* При `+0x4D == 0` и `[esi+0x10] == 0xC5735A11` вызов `0xB44930` выполняется на `0xA505A0` — непосредственно подтверждённая ветка **LZD-ID**. При других значениях используется `0x9C1250` (`0xA505C5`); для корректно прошедшего показанные проверки заголовка это оставшаяся ветвь LZX, но сам участок `0xA505A7` повторно не проверяет LZX-ID.
* В `0xB44930` при равенстве сравниваемых длин выполняется вызов копирующего помощника `0xF3B32C`; иначе вызываются вспомогательные процедуры и обрабатывается битовое состояние. Это подтверждает наличие отдельного обработчика для LZD-ID, но полная спецификация LZD, совместимость с другими реализациями, корректность и обработка повреждённых входов здесь не доказаны.
* `0xE5A3A0` вызывает `0xF023C0`; `0x9C1250` вызывает `0xF0C4CC`, `0xF0C48F`, `0xF0C4F1`. Установлена связь вызовов, но имена библиотечных алгоритмов у этих вложенных функций без независимого сигнатурного или динамического подтверждения не присваиваются.

Все сырые little-endian совпадения этих ID в EXE перечислены в CSV: соответственно 5, 4 и 5. Их начало находится **внутри** инструкций — адреса в CSV не следует принимать за адреса начала команды. Приведённые в отчёте адреса проверены в дизассемблировании от рассмотренных границ.

## 4. Прочие упоминания ZLib и Lua/API

Остальные ZLib-строки относятся к диагностике `GFxZlibState` при чтении сжатого SWF/изображений и к общим сообщениям `zlib version/memory/unknown error`; в `.data` есть RTTI `GFxZlibSupportBase` и `GFxZlibSupport`. Это отдельное свидетельство наличия ZLib-связанных компонентов Scaleform/GFx, **не доказанная связь с MiniPack**. Кандидаты прямых `push` на соответствующие начала строк перечислены в `xref-candidates.csv`; их контекст в этом отчёте отдельно не верифицировался.

В upstream API есть 15 путей вида `Despair.<Editor>.AutomationUtility.IsFileMiniPack`, включая `Despair.Forge.AutomationUtility.IsFileMiniPack`. Например, `external/lua-api/snapshot/docs/reference/Despair.Forge.AutomationUtility.md:299` содержит call-tip: `fileName`; результат true для mini pack, false в противном случае или при ошибке. Запись присутствует и в `api/despair-api.json`, и в текстовом `luasense_bytecode_disassembly.txt`. Сигнатура в Lua-заглушках не восстановлена; само название и документация не показывают реализацию или привязку этого editor API к данному EXE. Отсутствие `LSD`, `LZD` и `ZLib` в снимке касается буквального поиска, а не отсутствия возможностей сжатия.

## Ограничения и повторный запуск

```sh
python tooling/install.py                    # при отсутствии локальных зависимостей
python tooling/fetch_lua_api.py              # только если external/lua-api отсутствует
python tooling/verify.py --exe 'evidence/source-exe/F.E.A.R. 3.exe'
python tooling/trace_compression.py
```

Нужен исходный EXE с указанным хешем; он не хранится в Git. Генератор проверяет хеш EXE, хеш snapshot ZIP и все файлы snapshot, проверяет RTTI/слоты, затем пересоздаёт CSV и выдержки. Вызов `verify.py` отдельно необходим для проверки извлечённых секций.

Объектные графы, косвенная диспетчеризация, другие кодировки, внутренности всех callee, сериализованный формат и все возможные межмодульные пути не исчерпаны. Raw-ссылки на `IO\\MiniPack` могут быть, например, метками аллокатора и не означают использования алгоритма. `xref-candidates.csv` не является полным графом вызовов; отчёт не утверждает, что просмотрены все возможные косвенные пути. Для окончательной связи MiniPack с компрессией нужны дальнейшая межпроцедурная трассировка и/или контролируемая проверка на подлинных файлах и совместимой среде.
